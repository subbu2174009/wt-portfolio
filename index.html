Problem Statement

Organizations often face difficulties in managing tasks, tracking employee progress, monitoring deadlines, and maintaining communication between managers and employees. Traditional methods lead to delays, lack of transparency, poor accountability, and inefficient workload distribution.

WorkDist provides a centralized platform for task assignment, collaboration, monitoring, notifications, audit logging, and analytics.

Centralized Workforce Management Manage companies, managers, and employees from a single platform.

Use Case 1: Super Admin – System Oversight

Actors: Super Admin

Primary Actor: Super Admin

Purpose: To monitor high-level metrics and maintain accountability through audit trails.

Pre Conditions:

  • Super Admin is authenticated.
  • Super Admin is on the central dashboard.

Post Conditions:

  • System health is verified.
  • Audit logs are reviewed.

Main Success Scenario

  1. Super Admin logs into the system and views the dashboard containing total counts of managers, employees, and tasks.
  2. Super Admin searches for a specific manager using name or email.
  3. Super Admin opens the "Full Audit Log" to review all recorded system activities.
  4. Super Admin applies filters to the audit logs based on date range or activity type.
  5. Super Admin reviews system activities and identifies suspicious or inactive accounts.
  6. Super Admin selects a manager account and clicks "Deactivate" to restrict access.
  7. System updates the manager account status and records the action in the audit log.

Exceptional Scenarios

  • 1.a Invalid Login Credentials: If incorrect login credentials are entered, the system displays an "Invalid username or password" message.
  • 2.a No Data Found: If the search query returns no results, the system displays a "No matching managers found" message.
  • 2.b Invalid Search Input: If the search field contains unsupported characters or invalid input, the system prompts the user to enter valid search criteria.
  • 3.a Audit Log Retrieval Failure: If audit logs cannot be fetched due to a server/database issue, the system displays an error message.
  • 4.a Audit Overflow: If the number of logs is too large, the system enables pagination to maintain performance.
  • 4.b Invalid Filter Range: If the selected date range is invalid, the system prompts the user to choose a valid range.
  • 5.a Restricted Audit Access: If certain logs require higher privileges, the system restricts visibility to authorized Super Admins only.
  • 6.a Already Deactivated Account: If the selected manager account is already inactive, the system displays an appropriate status message.
  • 7.a Update Failure: If the account status update fails due to a server issue, the system displays a failure notification and keeps the previous status unchanged.

Architecture Overview

The Insurance Policy Management System is a robust multi-tier web application built using Vanilla Node.js on the backend (creating a routing controller via core modules to process raw HTTP requests, query parsing, and custom templated rendering) and a MySQL database backend to manage business models.

Main Core Modules Used
  • http / url / querystring: Form data handling, routing controller and payload parsing.
  • fs (FileSystem): Stream and read active HTML content blocks.
  • mysql2: Establishes connections and processes relational statements.
Database Schema Model (MySQL)

The system relies on six tables establishing relational dependencies:

• agents (agent_id, name, email, password, phone)
• customers (customer_id, name, email, password, phone, address)
• policies (policy_id, policy_name, premium_amount, duration, coverage, agent_id)
• applications (application_id, customer_id, policy_id, application_date, status)
• claims (claim_id, customer_id, policy_id, claim_amount, claim_status, claim_details)
• payments (payment_id, customer_id, amount, payment_date, payment_status)
